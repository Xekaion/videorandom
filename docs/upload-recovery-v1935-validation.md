# 1.9.35 · 업로드 응답 유실 복구와 대기열 진행

2026-10-28. 사용자 영상·음성·전사·요약·원시 제공자 응답은 열지 않았다. 실제 ASR·모델·GPU·번역 요청 없이, 허용된 기술 상태와 진단 필드만 확인했다. 운영 프로그램을 종료·교체·재시작하지 않았다. 검증에는 별도 저장소·포트의 중립 합성 자료와 소유한 HTTP 서버·실행 파일만 사용한다.

## 확인한 이번 중단

양쪽 실행 버전은 1.9.34였다. 클라이언트의 자료 업로드 시작은 한국 시각 2026-10-28 **01:04:57.227**, 오류는 **01:05:09.924**로 약 12.7초 후 `ECONNRESET`이었다. 실패 단계는 `upload`이며 번역 구간 수는 0이었다. 10분 업로드 제한 시간에 도달한 경우가 아니다. 이 실패를 공통 네트워크 장애로 처리해 후속 대기 영상도 일시 중단했다.

당시 기록에는 서버 접수 번호가 없었다. 이것만으로 서버가 접수하지 않았다고 단정할 수 없다. 기존 서버는 접수 전 업로드의 수신량·실패를 보관하지 않아 물리적 연결 단절, 서버 종료, 파일 저장·자료 검증 실패 가운데 무엇이 연결을 끊었는지는 과거 자료로 확정할 수 없다. 이후 새 작업 시작 기록도 있었으나, 수동 재개인지 자동 진행인지 추측하지 않는다.

## 접수 확인과 중복 방지

- `upload-receipts-v1`을 협상한 양쪽 프로그램은 32자리 업로드 확인 번호를 공유한다. 서버는 본문 수신 전에 접수 기록을 디스크에 생성하고, 전체 수신량과 자료 검증이 맞으면 접수 완료를 원자적으로 보관한 뒤 작업을 게시한다.
- POST 응답이 끊겨도 새 POST를 보내지 않는다. 같은 서버의 인증된 `/v1/uploads/:id` 읽기로 기존 접수를 확인한다. 완료된 접수는 같은 작업 번호의 결과로 이어받고, 접수 기록은 있으나 작업을 찾지 못하면 접수 사실을 유지한 채 기존 결과 복구로 넘긴다.
- 확인 번호·작업 번호·예상 크기·전체 수신량이 맞아야 기존 접수로 인정한다. 중복 확인 번호는 이미 있는 접수만 반환하며 새 작업을 생성하지 않는다. 조회 404도 미접수의 증거로 삼지 않는다.
- 업로드 확인 조회는 최대 네 번, 각각 3초 제한과 유한 대기 간격을 사용한다. 응답·연결이 조금씩 살아 있어도 절대 요청 제한 시간이 지나면 끝낸다. HTTP 오류 헤더, 응답 크기 초과, 사용자 취소와 최초 저장 오류를 이후 `aborted`/연결 끊김으로 덮지 않는다.
- 기록은 작업 임시 폴더 밖에 보관한다. 재시작 시 수신 중이던 접수는 중단으로 바꾸고 접수 완료 사실은 유지한다. 개별 손상 기록은 그 확인 번호에 대해서만 닫힌 상태로 남기며 정상인 다른 접수까지 막지 않는다. 명시적 서버 중지와 접수 저장이 겹쳐도 이전 요청이 재시작 후 새 작업으로 실행되지 않는다.

## 다음 독립 영상

앱의 실제 업로드 경계에서 확인한 `ECONNRESET`·`EPIPE`·`ETIMEDOUT`, 접수 불확실 상태, 동일 대상 서버에 대한 새 인증 상태 확인이 모두 있어야 `LAN_UPLOAD_INTERRUPTED`를 만든다. 이 증거가 있으면 확보한 결과를 미완료로 저장하고 다음 **독립 영상**을 진행한다. 같은 실패 영상을 자동 재전송하지 않으며, 사용자 중지·자동 분석 사용 안 함은 유지한다.

접수 기록의 명시적 저장·인증·사용량·제공자·미분류 오류, 다른 HTTP 오류, 충돌하는 원인 정보는 정상 상태 응답으로 무시하지 않는다. 고정 코드나 오류 문구만으로 대기열 재개 권한을 주지 않는다. 기존 일시 중단 기록에는 당시 서버의 신뢰할 만한 출처가 없어 과거 중지를 자동 해제하지 않는다. 기존 주소·연결 코드·원문·자막·부분 결과와 대기 목록은 보존한다.

## 기술 진단과 표시

서버 접수 전부터 시작·수신 실패·접수 완료를 기록한다. 새 기록에는 확인 번호, 수신 상태, 예상/수신 바이트, 경과 시간과 고정 오류 분류만 추가한다. 이 시점에는 검증하지 않은 클라이언트 신원을 만들지 않는다. 화면은 접수 여부 불확실과 접수 완료, 연결 확인과 분석 완료를 구분한다. 임의 오류 본문·경로·연결 코드·원시 제공자 출력은 새 기술 필드로 노출하지 않는다.

ASR 모델·정확도 옵션·원문 구간·검수 범위와 기존 번역 요청 제한은 변경하지 않았다. 이번 수정은 통신 중단 복구와 대기열 처리이며 실제 번역 서비스의 응답 속도나 모든 작업의 완성을 보장하는 변경은 아니다.

## 검증

- 실제 클라이언트 HTTP 업로드에서 완료 응답만 끊어 같은 접수 조회·결과 수신을 확인한다. 업로드는 정확히 한 번이며 다른 작업 번호·불완전 수신량·명시적 거부·HTTP 오류·알 수 없는 원인·사용자 취소가 접수 성공이나 대기열 재개로 바뀌지 않는다.
- 서버의 수신 중 연결 단절, 최초 저장 오류, 중복 확인 번호, 접수 저장 전후 중지, 재시작, 손상된 개별 기록을 별도 디렉터리와 소유한 HTTP 연결로 검증한다.
- 부분 자막 `1/3`과 오류 기록을 저장한 뒤 다음 두 독립 작업이 순서대로 한 번씩 실행되고, 기존 중지와 실제 저장·인증 오류가 보호되는지 대기열 서비스의 HTTP 경로로 확인한다. 전체 재분석과 번역 복구의 예외 전달 경로를 모두 포함한다.
- 요청 버퍼는 응답 크기 초과의 최초 오류, 잘린 HTTP 401/429/503 본문, 취소와 지속적인 소량 응답의 절대 제한 시간을 검증한다. 숨겨진 제공자 오류·저장 오류·알 수 없는 속성으로 전송 복구나 재개 권한을 만들지 않는다.
- 진단 화면에는 허용한 상태·크기·시간만 표시되며 임의 기술 본문이 삽입되지 않는지 DOM 모형으로 확인한다.
