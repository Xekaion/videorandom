# 1.9.1 · 음성 인식 처리 대기와 저장 낭비

2026-10-18. 1.9.0을 기준으로 정확 모드의 모델·입력 범위·인식 인수·원어 및 한국어 검수 기준을 유지하면서 처리 대기와 중복 계산을 줄인다. 사용자 영상·대사·이미지는 열거나 분석하지 않으며 운영 분석 서버를 중지·재시작하지 않는다.

## 변경과 경계

정확 모드는 여전히 `large-v3`, beam 5, 온도 재시도, 단어별 시간 정렬, 전체 음성 처리와 누락 재검수를 사용한다. 속도 우선 선택을 기존 정확 모드 사용자에게 강제로 적용하지 않는다. recognition revision 3과 한국어 번역 검증 버전 4, 같은 입력의 체크포인트 키를 유지한다.

두 구간 병렬 디코더는 완료 결과를 CPU 후처리에 넘기기 전에 다음 작업을 제출한다. 동시에 실행하거나 대기하는 future는 최대 두 개이며, 호출자가 처리하는 완료 결과 한 개가 별도로 존재할 수 있다. 결과는 원본 순서로 반영한다. 메모리 부족 시 진행 중인 작업을 정리하고 성공한 결과를 유지하며 실패한 구간만 같은 모델·인수로 한 번 순차 재시도한다. 관련 없는 실패는 이 경로로 재시도하지 않는다.

NVIDIA 메모리 확인 도구는 PATH에 있는 실행 파일을 먼저 찾고 Windows의 System32·NVSMI 정상 설치 위치도 확인한다. 불명확한 CUDA 장치 매핑이나 메모리를 확인하지 못한 환경에서는 자동 병렬 처리를 하지 않는다. 총 메모리 8GiB 이상·준비 전 여유 4GiB 이상에서 두 작업을 조건부로 준비하고, 준비 후 여유 2GiB를 다시 확인한다. 이는 이전의 준비 전 6GiB 조건을 조정한 것이며 실제 디코더의 모든 최대 메모리 사용을 보증하지 않는다. 준비 및 디코딩 중 메모리 부족 복구는 계속 적용된다.

대사 수를 N이라고 할 때 매 대사마다 누적 배열을 복사하던 경로는 총 N(N+1)/2개 참조를 복사했다. 이제 해당 분석이 소유한 배열에 추가하고 실제 체크포인트를 만들 때만 스냅샷을 복사한다. 초기 원문, 실패 시 복원 원문, 감사 후 최종 원문은 분리하여 보존한다.

주기적인 원문 저장은 진행 중인 쓰기 한 개와 최신 대기 한 개로 합친다. 분석 전·실패 시·최종 저장 같은 명시적 경계는 호출 순서를 유지하는 장벽이며, 반환 전에 이전 저장과 최종 저장을 마무리한다. 쓰기 실패 경고는 유지한다. 번역 체크포인트는 같은 원문 지문과 직렬화한 JSON을 재사용하되, 같은 원문의 더 긴 검증 결과를 짧은 진척으로 덮지 않는 검사는 유지한다.

모델·정확/빠름·장치·연산 형식·병렬 수는 실제 워커가 보낸 값만 진행 경로로 전달한다. 경로·연결 코드·임의 명령 등은 허용하지 않는다. 한 작업의 같은 파일에서 확인된 값만 이후 단계의 사용 기록으로 보관하며 다음 파일·새 작업에는 이월하지 않는다. 현재 화면의 선택을 실제 사용 모델이라고 표시하지 않는다. 속도 우선 설정의 저장 완료 문구는 서버 저장 성공 후 해당 선택이 여전히 최신일 때만 표시한다.

## 합성 검증과 실제 속도의 구분

모의 모델과 CPU 처리 게이트로 현재 결과의 후처리가 멈춘 동안 다음 구간이 시작되는지, 네 번째 구간은 아직 제출하지 않는지, 최대 동시 실행 두 개와 결과 순서를 확인한다. 같은 인식 인수·대사 시각·검수 결과와 메모리 부족 시 성공 결과 보존·실패만 한 번 재시도를 검사한다. 메모리 사전·사후 경계와 도구 탐색은 모의 응답으로 확인하며 이 검사에서 모델이나 GPU 추론을 실행하지 않는다.

독립 저장 폴더의 느린 쓰기 모형에서는 주기 저장 요청 10,000개가 최초·최신 두 번의 쓰기로 합쳐진다. 명시적 저장 경계·최종 flush·쓰기 실패 경고와 원래 원문 보존도 확인한다. 161개 합성 원문 구간의 번역 저장은 원문 지문 반복 계산 상한, 기록과 내용 인덱스의 같은 JSON 바이트, 더 긴 검증 결과 보존을 확인한다.

이 수치는 제거한 복사·쓰기·대기 작업의 근거다. 실제 사용자 영상의 음성 인식 시간, 인식률, 몇 배의 속도 향상을 측정한 결과가 아니다. 새 버전은 입력 음성 길이와 단계별 처리량을 계속 표시하므로 같은 공개·사용 허가 자료와 같은 장치로 후속 비교할 수 있다. 원어·한국어 검수 완료를 속도 때문에 임의로 인정하지 않는다.

## 1.9.1 배포 확인 결과

* 최종 전체 Node 검사: `node --test --test-timeout=60000 test/*.test.js`, **663개 통과, 실패·취소·건너뛰기 0개**, 약 27.5초. 음성 인식 Python 모의 검사도 **99개 통과**했다. 실제 모델 추론은 실행하지 않았다.
* 최초의 제한 없는 `npm test`에서는 변경하지 않은 복구 테스트 파일이 종료되지 않았다. 정확한 원인은 재현하지 못했다. 직접 시작한 해당 테스트 자식만 신원을 확인해 종료했고, 그 파일의 단독 검사 13개 및 제한 시간을 둔 전체 재검사는 통과했다. 운영 프로세스에는 조치하지 않았다.
* `npm run build` 성공. Windows EXE는 **99,306,573바이트**, SHA-256은 `d3332378263c2fa2ca3e4736adea9fa91edc525c3b9f3d7fb958821fd671b2f6`이다. 생성한 `update.json`을 실제 파일 크기·해시·MZ 헤더와 다시 대조했으며 자산 주소는 `v1.9.1` 태그에 고정한다.
* 최종 EXE의 화면 자산이 소스와 일치했다. 독립 저장 폴더와 모의 LAN 서버에서 저장 결과 열기·수정, 한국어 번역만 복구, 원래 자막 시간과 영상 옆 SRT 저장, 기존 완성 자막·원문·사용자 일시 중지 보존을 확인했다.
* 별도로 복사한 **실제 1.9.0 EXE에서 1.9.1 EXE로 업데이트**하고 같은 포트·저장소에서 준비·활성화되는지 확인했다. 기대 버전을 의도적으로 다르게 만든 시작 실패에서는 기존 **1.9.0 EXE의 정확한 해시로 복구·재실행**됐다. 두 경로 모두 합성 분석 결과·SRT·중지한 대기열·암호화한 클라이언트 연결·서버 연결의 **5개 파일이 바이트 단위로 유지**됐다.

이 검증은 별도 테스트 EXE·포트·저장소에서 수행했다. 실행 중인 운영 분석 서버를 교체하지 않았으며 실제 사용자 영상의 속도나 분석 완료를 입증하는 검사가 아니다. 1.9.0 Windows EXE는 내장 업데이트를 이용할 수 있고, 1.6.5 같은 이전 버전은 작업 종료 후 처음 한 번 새 EXE로 교체해야 한다. Node 소스 실행에는 EXE 자동 교체를 적용하지 않는다.
