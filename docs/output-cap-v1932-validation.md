# 1.9.32 · 요청 출력 제한과 대기열 진행

2026-10-27. 실제 사용자 미디어·원문 대사·제공자 원시 응답을 읽거나 실제 ASR·번역 요청을 실행하지 않고, 보고된 오류 문자열과 현재 코드 경로를 대조해 중립 fake CLI·저장소·HTTP 회귀로 검증했다.

## 원인과 구분

`incomplete response returned, reason: max_output_tokens`를 CLI의 `turn.failed`/`error` 또는 오류 출력으로 받으면 기존 코드가 일반 실행 실패로 감쌌다. 전용 유형이 없어 `DIAGNOSTIC_UNKNOWN`/`PROVIDER_UNKNOWN`과 `executionSource: provider-error`가 저장됐고, 대기열의 공유 환경 오류 정책이 모든 후속 영상을 일시 중지했다. 공용 함수가 번역 요청에도 ‘Codex 요약 실패’라고 붙이는 표시 오류도 있었다.

이 표시는 요청 한 건의 출력 제한이며 계정의 사용량 소진과 다르다. 현재 API 키 없는 Codex CLI 실행 인수에는 `max_output_tokens` 수치가 없다. 실제 서비스의 설정 수치·내부 원인은 이 코드와 오류 한 줄로 확정할 수 없다. 별도 API 키 경로의 출력 인수나 로컬 stdout/JSON 바이트 방어 한도를 이 원인으로 혼동하지 않는다. CLI의 지원 여부를 확인하지 않은 인수·모델 변경·무한 재시도는 추가하지 않았다.

## 변경

- 정확한 전체 기술 오류만 `providerErrorType: output-limit`, `PROVIDER_OUTPUT_LIMIT`로 분류한다. CLI 오류 이벤트·bounded 오류 출력만 근거이며 프롬프트·일반 응답 JSON·대사 안의 같은 문구·임의 접두어·추가 payload는 권한이 아니다. 고정 한국어 설명과 제한된 기술 필드만 저장·전달한다.
- 실제 요청별 출력 제한은 같은 요청을 다시 보내지 않는다. 요약 요청만 이 상태라면 기존 요약·장면·전체 원문을 보존하고 요청된 한국어 자막을 원문 기준으로 처리한다. 미완성 JSON을 정상 결과로 사용하거나 요약을 완료로 인증하지 않는다. 번역의 출력 제한은 검증된 자막·원문·시각·체크포인트를 보존한다.
- 결과와 종료 기록을 저장한 뒤 다음 독립 대기 영상을 처리한다. 실패 영상의 무한 재등록은 하지 않는다. 원인별 복구 안내도 계정 사용량 오류 대신 출력 제한과 다음 대기 영상 진행을 표시한다.
- 구버전의 정확한 원본 오류와 같은 시도의 summary 단계 UNKNOWN 진단만 좁게 인정해 기존 `attempt-failed` 일시중지에서 후속 목록을 이어간다. 새 실행을 통해 기존 큐의 복구 절차를 이용하며 사용자 중지·취소·다른 시도·불명 원인·다른 공유 환경 오류는 해제하지 않는다.
- 인증·사용량 한도·거절·통신·저장·서비스 상태·시간 초과·취소는 우선한다. 겹친 요약 구간의 출력 제한으로 다른 구간을 정리하는 도중 실제 서비스 오류가 도착하면 그 관측을 풀의 실패로 보존한다. 내부 정리용 취소가 실제 오류를 숨겨 번역을 시작하지 않게 한다. 이 집계는 추가 요청·모델 변경·재시도 권한을 주지 않는다.
- 번역 CLI 실패에는 ‘Codex 자막 번역 실패’로 단계를 정확히 표시한다. 1.9.30의 정확 모드 성능 개선과 1.9.31의 고정 업데이트 조회 경로를 유지한다.

## 검증

- 신규 실행 진단 87개와 기존 11개: 정확한 기술 마커·분할 UTF-8·오류 이벤트·오인 방지·동시 hard 근거의 전후 순서·sanitize·LAN JSON 투영. 명시된 공유 오류나 보관 진단을 출력 제한으로 낮추지 않는다. 바로 한 단계 원인의 인증·사용량·거절·통신·서비스 상태·취소·시간 초과를 코드 유무와 관계없이 안전하게 보존하며, 설명되지 않은 원인이 있으면 출력 제한의 계속 처리 권한으로 바꾸지 않는다.
- 신규 큐 33개와 관련 기존 250개: 저장 후 FIFO 후속 영상 1회 진행, 현재 부분 자막/SRT 보존, 중복 요청 없음, 재실행 후 정확한 과거 일시중지 복구, 사용자 중지·hard 오류·불명 원인 보호.
- 신규 fake provider 통합 12개: 요약 1회 출력 제한 뒤 원문 그대로 번역, 기존 요약 보존, 긴 원문의 시작된 최대 두 구간 정리·미시작 구간과 최종 요약 호출 없음, 실제 인증·사용량·거절·503·사용자 취소 우선, 번역 부분 결과 유지, 응답 JSON의 위장 코드 거절, 어느 구간이 먼저 실패하든 정리 도중 실제 503 경합. 관련 기존 provider·summary 검사와 함께 통과했다.
- 신규 복구 안내 9개와 기존 안내 검사: 출력 제한 설명·계정 사용량과 구분·수동 복구·불명 오류 및 실제 공유 오류 우선·원본 불변.

## 전체 검사에서 발견한 소유권 경합

첫 전체 검사에서 기존 `simultaneous stale-lease recovery elects one live owner`가 실패했다. 단순 시간 제한 문제로 생략하지 않았다. 명시적 IPC 시작·해제를 쓰는 별도 중립 시험에서 67회차에 두 프로세스가 살아 있는 채 동시에 소유권을 반환하고, 두 번째 PID의 파일만 남는 현상을 재현했다. Windows의 지연된 두 source handle이 같은 과거 inode를 연속 이름 변경할 수 있는 경로와 일치했다. `artifacts/lease-race-v1932-observation.json`.

과거 소유 파일을 새 PID 이름으로 가져오는 rename을 제거했다. 검증된 정확한 과거 파일명만 지운 뒤 비어 있는 디렉터리를 정리하고, 기존 fresh mkdir·고유 준비 파일 공개 절차로 새 소유권을 얻는다. 새로운 살아 있는 고유 파일을 늦은 정리로 지우지 않으며, 비어 있는 공개 순간이 제거된 시작 시도는 안전하게 실패한다. PID·nonce·JSON 검증, 살아 있는 소유자·알 수 없는 파일·손상 자료 거절, 부분 공개의 30초 보호와 자기 파일만 해제하는 검사를 유지한다.

신규 결정적 VM·실제 IPC 검사 8개와 기존 서버 복원 검사 14개를 통과했다. 6개 시험 자식의 명시적 시작·종료를 5회 검사해 소유자 정확히 1명·생존·현재 claim PID 일치까지 확인했다. 같은 결정적 검사에 1.9.31 소스만 주입하면 두 번째 소유자가 반환돼 실패함을 확인했다. 실제 운영 프로세스·저장소에는 접근하지 않았다. `artifacts/lease-v1931-baseline-regression.log`.
