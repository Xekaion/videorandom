# 반복 사용을 위한 운영 개선 · 1.7.0

2026-10-16. 개인 PC와 같은 내부망의 여러 PC에서 반복 실행할 때의 목록 반응성·중단 복구·중복 실행·오류 처리를 개선했습니다. 실제 사용자 영상, 대사, 분석 결과와 운영 서버는 검증에 사용하거나 변경하지 않았습니다.

## 목록 전송과 상세 화면

기존 `/results`, `/jobs/:id`, `/auto-pick`, `/config`는 저장된 전체 원문·번역·단어 진단을 응답했습니다. 화면은 `?view=summary`를 사용해 목록용 메타데이터, 대사 수, 이미지 수, 첫 이미지 3개만 받습니다. 검색용 요약·줄거리·라벨은 유지합니다. 기존 전체 응답 API는 호환성을 위해 계속 제공합니다.

상세 화면은 `GET /results/:id`로 해당 결과만 읽습니다. 이미 읽은 결과는 같은 저장 시각의 목록 요약으로 덮지 않습니다. 상세를 닫거나 다른 영상을 선택한 뒤 늦게 도착한 응답은 화면을 바꾸지 않습니다. 불러오는 동안 빈 편집 폼을 저장할 수 없습니다. 긴 대사는 첫 200구간부터 표시하고 **대사 더 보기**로 추가합니다. 다운로드와 내보내기는 서버의 전체 자료를 사용합니다.

`node --test test/catalog-summary.test.js`의 일반 안내 문장 합성 자료 50개 × 1,000대사 측정:

| 항목 | 전체 응답 | 목록 응답 |
| --- | ---: | ---: |
| JSON 바이트 | 7,730,623 | 55,973 |
| 감소 | — | 99.276% |

추가 heap과 두 응답은 시험에서 각각 30MiB 미만입니다. 직렬화 시간은 실행 부하에 따라 달라지므로 처리 성능 보장 수치로 사용하지 않습니다. 이 수치는 영상 디코딩·음성 인식·번역 속도의 측정이 아닙니다.

## 환경 확인 중복 실행

`getProviderStatus`는 같은 데이터 폴더의 진행 중인 검사 Promise를 공유합니다. 동시 요청 8개에서 Codex·Python 상태 하위 프로세스 실행 수가 16개에서 2개로 줄었습니다. 기본 15초 결과 캐시와 캐시 비활성화 설정, 데이터 폴더별 분리, 실패 후 다시 검사하는 동작을 유지합니다. 실제 Codex 요청이나 음성 모델은 실행하지 않은 모형 시험입니다.

## 작업 기록과 명시적 재개

1.7.0에서 새로 시작한 수동 선택·복구 분석은 provider 호출 전에 `jobs.json`을 임시 파일에 쓰고 sync·rename으로 보관합니다. 이전 버전에 저장되지 않았던 수동 작업 목록을 소급해 복원하지는 않습니다. 결과도 파일별로 sync·rename을 마친 뒤 작업 진행 경계를 갱신합니다. 작업 기록에는 원본 경로·크기·수정 시각·시도 ID·안전한 분석 옵션을 저장하고, 연결 코드·API 키·대사·번역·repairRecord를 저장하지 않습니다. 기록은 8MiB와 20작업으로 제한하고 미해결 중단 작업을 조용히 버리지 않습니다.

재실행은 `running` 작업을 `interrupted`로 복원합니다. 작업 기록의 완료 ID만 믿지 않고 실제로 읽을 수 있는 같은 ID·원본 경로의 결과 JSON과 대조합니다. 결과가 먼저 저장되고 작업 경계가 갱신되기 전에 종료돼도 해당 결과를 다시 요청하지 않습니다. 반대로 완료 ID만 있고 결과가 없으면 미처리 파일로 표시합니다.

`/config.interruptedJobs`와 `POST /jobs/:id/resume`가 이를 제공합니다. 재개는 사용자가 버튼을 눌렀을 때만 실행합니다. 원본의 크기·수정 시각과 현재 도구·연결을 다시 확인하며, 미처리 파일에 새 시도 ID를 부여하고 이전 결과를 보존합니다. 재개 요청은 기존 작업 시작·취소와 같은 잠금으로 직렬화합니다. 취소한 작업은 중단 복원 목록에서 제외합니다. 손상된 작업 기록은 원본을 보존하고 오류를 표시하며 수동 작업 시작을 막습니다.

현재 파일의 음성 인식 내부 시점부터 재개하는 기능은 없습니다. 해당 파일은 처음부터 다시 처리합니다. 저장된 부분·실패 결과도 이미 처리한 결과로 보존하므로, 그 영상을 다시 검수하려면 상세 화면에서 **복구 / 다시 분석**을 선택합니다. 원본이 바뀌었거나 필요 없는 중단 작업은 **이 대기 작업 취소**로 제외할 수 있습니다. `POST /jobs/:id/dismiss`는 중단된 대기의 상태만 취소로 바꾸고 저장된 결과와 원본 파일을 삭제하지 않습니다.

## 짧은 LAN 연결 끊김

분석 서버가 이미 접수한 작업의 상태 GET에서 연결 리셋·시간 초과 등의 네트워크 오류가 나면 같은 작업 ID로 최대 3회 다시 확인합니다. 추가 대기는 250·500·1,000ms이며 각 GET의 기존 30초 타임아웃을 유지합니다. 연결 복구 중임을 진행 화면에 표시합니다. 대기 중 사용자가 취소하면 즉시 중단합니다.

첫 연결 확인·업로드 POST는 재제출하지 않습니다. HTTP 401·403·429·503과 provider의 최종 실패·거절도 재시도하지 않습니다. 제한을 소진하면 서버에서 기존 작업이 계속 실행 중일 수 있음을 안내합니다. 이는 원격 작업을 새로 요청하는 재시도나 서버 재시작 후의 작업 복원이 아닙니다. 소유 테스트 HTTP 서버로 13개 회귀를 확인했습니다.

## 시간 기록

작업의 완료 상태는 최종 작업 기록 저장과 실행 잠금 해제가 끝난 뒤 동시에 공개합니다. LAN 호스트도 업로드 음성 파일의 정리를 마친 뒤 완료·실패·대기 취소를 공개합니다. 파일 정리와 기록 쓰기를 시험용 gate로 멈춰 이 순서를 검증했으며, 임의의 대기 시간을 추가해 완료를 맞추지 않았습니다.

진행 응답은 `elapsedMs`, `stageElapsedMs`, `stageKey`, `lastProgressAt`을 제공합니다. 파일 결과는 `analysisMetrics.totalMs`와 단계별 시간을 보관합니다. 단계 이름은 허용된 작업 분류로 제한해 경로·대사를 진단 지표에 넣지 않습니다. 완료 후 경과 시간은 고정됩니다. 남은 시간은 추정하지 않습니다. 이 값은 경과한 벽시계 시간이며 CPU/GPU의 순수 연산 시간과는 다릅니다.

## 시작과 요청 오류

프로그램은 로컬 리스너를 확보한 뒤 저장 폴더의 PID·nonce 소유권을 얻고 분석·히스토리 서비스를 생성합니다. 같은 버전을 다시 열면 기존 화면을 재사용하며, 같은 저장 폴더의 다른 실행 파일이 작업을 동시에 복원하지 못합니다. 종료된 프로세스의 소유권만 회수하고 새 소유자의 nonce 파일은 삭제하지 않습니다. 동시 stale 회수 요청 6개에서 살아 있는 소유자 1개만 허용했습니다.

`app-info`는 원본 경로 대신 SHA256 `dataStoreId`와 준비 상태를 제공합니다. 준비 중 API는 JSON 503을 응답합니다. 시작 중 발견한 이전 버전은 종료 후 새 버전을 다시 실행하라는 안내를 제공하며, 실행 중인 다른 프로그램을 강제로 종료하지 않습니다. 예전 버전이 식별 정보·잠금 없이 검사하지 않은 포트에서 실행 중인 경우에는 새 버전이 이를 확정적으로 알아낼 수 없습니다. 업데이트 전 이전 프로그램을 닫아야 합니다.

Express 4의 비동기 거절을 오류 처리기로 전달하고 스캔·파일 경로 입력의 타입·길이·제외 목록을 검사합니다. 잘못된 요청은 400, 너무 큰 JSON은 413으로 응답합니다. 합성 자료의 실제 소유 테스트 프로세스에서 비정상 스캔·재생·폴더 열기 입력 뒤에도 app-info와 정상 빈 폴더 스캔이 계속 동작하는 것을 확인했습니다. 실제 플레이어·폴더 대화상자·사용자 파일은 실행하지 않았습니다.

## 이번 범위와 남은 운영 경계

Windows에서는 소유권 파일을 읽는 다른 프로세스 때문에 파일 교체가 `EPERM`으로 실패할 수 있었습니다. 종료된 소유자의 정확한 파일명만 새 PID·nonce 파일명으로 원자적으로 옮기는 방식으로 변경했습니다. 초기 게시 중인 빈 잠금 폴더는 회수하지 않으며, 30초 이상 남은 빈 폴더만 고아 후보로 검사합니다. 소유권 확인 뒤의 실패와 강제 종료도 별도로 검증합니다.

최종 전체 회귀 **376개가 통과**했습니다(실패·취소·생략 0). 잠금 회수는 추가로 6프로세스 동시 시작 30회를 실행해 매회 소유자 1개와 대기 거절 5개를 확인했습니다. 새 단계별 시간·목록 경량화·부분 자막 저장·명시적 작업 재개는 합성 열차 안내 자료를 사용한 실제 브라우저에서도 확인했습니다. 남은 한 파일만 처리되고 기존 결과를 포함해 두 결과가 보관됐습니다.

최종 빌드한 1.7.0 EXE도 별도의 데이터 폴더와 포트에서 실행했습니다. HTML·JS·CSS 바이트 일치, 준비 상태, 목록 요약과 전체 상세, 중단 작업 취소, 원래 시각의 부분 SRT 생성과 기존 완성본 보존, 편집 결과의 디스크 저장, 잘못된 요청 400 응답 뒤 정상 app-info를 확인했습니다. 이 시험에서는 실제 provider·음성 인식·영상 재생을 호출하지 않았고 운영 서버도 변경하지 않았습니다.

이 버전은 LAN·로컬 프로그램의 운영 기반 개선입니다. 외부 인터넷 공개, 여러 사용자의 로그인·요금제·상용 서비스 운영을 추가하지 않았습니다. 기존 연결 코드와 로컬 기록을 유지하며 API 키를 요구하지 않습니다.

Whisper 모델·음성 인식 기준·한국어 번역 및 검수 방식은 1.6.6을 유지합니다. 정확도 검증과 남은 불확실성은 [자막 재검수 검증](subtitle-recovery-validation.md)에 구분돼 있습니다. 이번 목록 측정으로 자막 인식률이 높아졌다고 판단하지 않습니다. 모델 상주 재사용·번역 묶음 확대는 별도 품질·메모리 측정이 필요해 적용하지 않았습니다.

LAN 호스트의 업로드 작업 큐는 아직 메모리 기반입니다. 서버 PC를 재시작하면 진행 중인 원격 작업 ID를 그대로 복원하지 못합니다. 원격 작업 수신 전에는 클라이언트 프로그램도 계속 켜 두어야 합니다. 예전 완료 결과의 원본 교체·모든 설정 변경을 자동 뽑기 캐시가 항상 감지하는 것은 아니므로 해당 경우 명시적으로 다시 분석해야 합니다.

검증은 자동 회귀, 실제 소유 테스트 프로세스, 합성 자료 브라우저 조작으로 수행합니다. 자세한 재현 테스트는 `test/catalog-summary.test.js`, `test/job-recovery.test.js`, `test/job-metrics.test.js`, `test/server-resilience.test.js`, `test/auto-pick-ui.test.js`에 있습니다. 운영 서버를 중지·재시작하거나 다른 PC의 업데이트 상태를 확인한 검증은 아닙니다.
