# 1.9.0 · 내장 업데이트와 작업 보존

## 적용 방식

프로그램은 API 키 없이 이 저장소의 고정 HTTPS `update.json`을 확인한다. 게시된 호환 프로토콜 1의 버전·정확한 바이트 수·SHA-256과 Windows 실행 파일의 MZ 헤더를 검사하여 실행 중인 파일과 별도 위치에 다운로드한다. 임의의 주소·경로·명령을 화면이나 업데이트 요청에서 받지 않는다. `npm run build`의 `postbuild`가 실제 빌드 파일로 배포 명세를 생성한다.

실행 파일은 명세의 버전과 같은 `v<version>` 배포 태그에 고정한다. 변하는 `main` 경로의 파일을 조합하지 않으므로 명세와 실행 파일의 캐시 시점이 달라도 서로 다른 배포 파일을 받지 않는다. 배포는 코드·실행 파일·명세를 같은 커밋에 넣고 그 커밋에 버전 태그를 붙인 뒤 `main`과 태그를 원자적으로 함께 게시한다. 기존 배포 태그를 덮어쓰지 않는다.

자동 확인은 시작 후와 약 5분 간격이다. 기본 자동 적용을 끄면 확인·알림만 수행한다. 설정이 손상된 경우 자동 적용을 켜지 않는다. 실패한 버전은 자동으로 반복 설치하지 않으며 사용자가 수동으로 다시 시도할 수 있다.

현재 작업이 끝날 때까지는 기존 분석·번역·업로드·저장 흐름을 유지한다. 유휴 상태에서 입장을 닫고 다시 상태를 검사한 뒤 저장과 히스토리를 마무리한다. 자동 분석 대기와 사용자의 일시 중지 이유는 변경하지 않는다. 원격 서버는 완료 결과를 원자적으로 저장하며 재시작 후 같은 작업 ID로 복원하므로 결과를 받기 전 앱이 바뀌어도 다시 가져올 수 있다.

## 교체와 복구 경계

Windows 도우미가 파일·체크섬·기존 프로세스의 실행 경로를 확인하고 준비 응답을 보낸 뒤에만 앱이 정상 종료한다. 도우미는 기존 앱을 강제로 종료하지 않는다. 종료를 확인한 후 검증된 새 파일을 복사하고 기존 파일을 고유한 백업 경로에 보관한다. 같은 포트·데이터 폴더·분석 서버 상태·연결 설정으로 새 버전을 시작한다.

새 앱의 시작 확인 동안에는 작업을 실행하지 않는다. 앱 이름·버전·저장소 식별자·준비 상태를 확인한 뒤 활성화한다. 시작에 실패하면 이 도우미가 직접 만든 비활성 새 프로세스만 종료하고 이전 파일을 복원한다. 파일 교체 전 실패도 기존 파일을 확인한 뒤 재실행한다. 활성화를 시작한 이후에는 작업을 중단하거나 이전 버전으로 되돌리지 않는다. 시작 확인 오류는 화면에서 확인하고 다시 시도할 수 있다.

업데이트 실패나 저장 오류가 있으면 기존 데이터와 검증된 파일을 보관하고 적용을 중단한다. 새 버전의 데이터 형식에 역호환되지 않는 변경을 도입할 때에는 업데이트 호환 프로토콜도 별도로 바꿔야 한다.

## 검증 범위

합성 대사·모의 다운로드·독립 저장 폴더와 직접 만든 테스트 프로세스만 사용한다. 운영 서버를 중지·재시작하거나 실제 사용자 영상·대사·이미지를 열지 않는다. 자동 업데이트 테스트는 실제 AI·음성 인식이나 GitHub 다운로드를 호출하지 않는다.

다운로드 검증, 중복·실패·취소, 설정 보존, 작업 종료 대기, 사용자 중지 보존, LAN 완료 결과·이미지 복원, 저장 실패 시 종료 차단, 같은 저장소의 새 버전 확인 후 화면 갱신을 회귀 검사한다. 실제 실행 파일의 교체·시작 확인·이전 버전 복구는 작업 폴더 안에 복사한 별도 EXE에서 확인한다.

## 1.9.0 배포 확인 결과 · 2026-10-16

* `npm test`: **649개 통과, 실패 0개**. 다운로드·컨트롤러·브라우저 복귀·Windows 도우미·작업 종료 대기·저장 경계를 포함한다.
* `npm run build`: Windows EXE와 `update.json` 생성 성공. 실행 파일은 **99,300,079바이트**, SHA-256은 `109fa32aa430c10c2788a70f25662f88e9d62486ee381f8743fa40a6b4ddd9ae`다. 생성 명세를 실제 파일과 다시 대조했고 버전 태그 주소도 검증했다.
* 실제 Windows 인계 검사: 별도 복사한 EXE에서 도우미 준비 응답 전 부모가 유지되는지, 부모 종료 후 같은 포트·저장소로 시작하고 활성화되는지 확인했다. 의도적으로 기대 버전을 다르게 만든 시작 실패에서도 이전 실행 파일 복원과 재실행을 확인했다. 실행 파일에서 자식 프로세스로 상속되는 `PKG_EXECPATH` 환경도 재현했다.
* 두 인계 경로 모두 합성 분석 결과·SRT·사용자가 중지한 대기열·암호화한 클라이언트 연결·서버 연결의 **5개 파일이 바이트 단위로 유지**됐다. 테스트 프로세스와 저장 폴더는 운영 서버와 분리했다.
* 최종 EXE의 화면 자산, 저장 결과 열기·수정, 한국어 번역만 복구, 원래 자막 시각, 영상 옆 SRT 저장, 기존 완성 자막과 사용자 일시 중지 보존도 합성 자료로 확인했다. 실제 AI·음성 인식 호출이나 사용자 영상 접근은 하지 않았다.

이 검증은 자동 교체와 기존 기능의 회귀 범위다. 새 버전에서 실제 사용자 영상의 인식·번역이 완료됐다는 의미는 아니다. 1.9.0 이전 프로그램에는 이 기능이 없으므로 양쪽 PC에서 처음 한 번은 기존 프로그램을 종료하고 새 Windows EXE로 실행해야 한다. Node 소스로 실행하는 서버에는 실행 파일 자동 교체를 적용하지 않는다.
