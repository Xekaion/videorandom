# 1.9.5 분석 작업 화면·대기열·예상 시간 검증

## 바뀐 동작

영상 내용 목록 위에 현재 작업 카드와 이 PC의 대기열을 배치한다. 현재 파일, 단계, 작업 전체 퍼센트, 경과 시간, 현재 단계 잔여 시간, 처리 영상 수를 표시한다. 부분 완료·실패·중지는 큰 100% 대신 해당 상태를 표시한다. 설정·저장 설명은 접어 작업 상태를 먼저 볼 수 있다. 목록은 파일명과 경로를 구분하고 재생·상세·대기 추가·복구를 제공한다. 파일명 아래의 짧은 상태 칩은 가로 스크롤 없이 대기·진행·완료·복구 필요를 알린다. 상태는 색상과 문구로 표시한다.

수동 대기 추가는 현재 작업 실행 중에도 허용한다. 등록된 스캔 파일 또는 저장 결과의 경로만 받으며 입력 전체를 검증한 뒤 대기를 한 번에 저장한다. 등록하지 않은 파일·사라진 파일·영상이 아닌 경로는 거절한다. 최대 대기는 1,000개이며 같은 영상과 현재 묶음 소유 파일을 중복 추가하지 않는다. 완료 결과를 선택하면 명시적인 새 분석을 대기시킬 수 있다. 자동으로 뽑힌 대기를 수동 선택하면 한 항목으로 승격한다.

기존 `auto-pick.json`에 수동 출처와 비밀을 제외한 항목별 설정을 보관한다. 연결 코드·API 키는 항목에 저장하지 않는다. 자동 뽑기 분석이 꺼져 있어도 수동 대기는 처리하며, 명시적인 대기 일시 중지는 둘 다 멈춘다. 현재 실행 중인 작업을 취소하거나 원본·결과를 삭제하지 않는다. 이미 현재 작업에 포함된 다음 영상은 조회만 가능하다. 정렬·제거는 별도 추가 대기에만 적용한다. 결과 저장 직후 종료된 경우 시도 ID와 결과 경로를 대조해 중복 실행을 피한다. 실패·중단한 시도는 사용자 확인 후 재개한다.

## API

| 경로 | 동작 |
| --- | --- |
| `GET /api/analysis/queue?view=summary` | 이 PC 대기·현재 묶음·현재 작업·일시 중지 원인 |
| `POST /api/analysis/queue` | `{files,options?}` 검증 후 수동 추가 |
| `PUT /api/analysis/queue` | `{paused:boolean}` 일시 중지·재개 |
| `POST /api/analysis/queue/move` | `{filePath,position}` 1부터 시작하는 대기 위치 변경 |
| `DELETE /api/analysis/queue/pending` | `{filePath?}` 개별 제거 또는 추가 대기 비우기 |

`scope: this-pc`, `sharedHostQueueKnown: false`로 범위를 명시한다. 서버가 다른 PC의 모든 로컬 대기를 안다고 표시하지 않는다. 기존 자동 뽑기 설정·접수 API는 유지한다. 업데이트 준비 중 신규 작업을 시작하지 않는 기존 게이트도 유지한다.

구버전 프로그램이 새 정적 화면을 제공하는 경우 `/queue`의 404에 한해 기존 `/auto-pick`으로 상태 조회를 이어간다. 새 관리 버튼은 비활성화하고 1.9.5 재실행 안내를 표시한다. 인증·서비스 오류나 업데이트 중 503에는 이 호환 경로를 사용하지 않는다. 새 서버의 정상 응답을 확인하면 관리 기능을 다시 제공한다.

## 남은 시간의 근거

음성 인식·누락 재검수는 실제 처리한 음성 초를 사용한다. 번역은 최종 검수와 체크포인트 저장을 마친 원문 구간 수만 사용한다. 미검수 초안·미리 준비 중인 초안·저장된 재사용 앞부분은 이번 실행의 처리량으로 계산하지 않는다. 구간 요약은 응답 검증을 마친 묶음 수를 사용한다.

최소 두 번의 전진 관측과 15초 경과 후 전체 관측 창과 최근 처리 간격 중 더 느린 속도로 계산한다. 관측량 부족·새 단계·마지막 전체 요약 요청은 측정 중으로 표시한다. 새 완료가 120초 넘게 없으면 오래된 추정치를 숨기며, 일반적인 작업 생존 신호만으로 완료 관측 나이를 초기화하지 않는다. LAN 전달 과정의 경과 시간도 반영한다. 완료·실패·취소·정리 단계에는 이전 단계 잔여 시간을 유지하지 않는다.

큰 퍼센트는 기존 작업 전체 진행률이다. 예상 잔여 시간은 **현재 단계**에만 해당하며 이후 음성 검수·최종 요약·번역·저장·다른 PC 대기는 포함하지 않는다. 영상 길이와 퍼센트만으로 전체 완료 시각을 만들지 않는다.

## 검증 방식

모든 실행 검증은 직접 만든 합성 파일·가짜 엔진·별도 데이터 폴더와 사용하지 않는 포트에서 수행한다. 실제 사용자 영상·대사·이미지와 모델/GPU 또는 번역 서비스를 사용하지 않는다. 운영 서버와 분석 작업은 종료·교체하지 않는다.

단위·통합 검사는 실행 중 추가, 중복과 자동 항목 승격, 일괄 검증의 원자성, 순서·제거, 현재 묶음 보호, 자동 OFF 수동 실행, 명시 중지 보존, 실패 중지, 재시작 보존, 연결 코드 제외와 업데이트 게이트를 확인한다. ETA 검사는 시간 가짜 시계로 워밍업·재개 기준선·지연·오류·최종 상태와 LAN 전달을 확인한다. 브라우저에서는 합성 작업·대기 자료로 추가·순서 변경·제거·중지·재개, 진행 카드, 좁은 화면, 완료 및 오류 표시를 확인한다.

기존 1.9.4의 모델·신뢰도·자막 시각·전체 음성 범위·초안/검수·최종 순차 저장·누락 보완 예산을 바꾸지 않는다. 이번 버전은 대기 관리와 관측·화면을 개선하며 실제 긴 영상의 완료 시간을 단축했다고 주장하지 않는다.

## 최종 실행 결과

* `node --test --test-concurrency=4 --test-timeout=60000 test/*.test.js`: **850 통과, 실패·취소·생략 0**, 60,547ms. 합성 입력에 대한 검사 시간이며 영상 분석 성능 수치가 아니다.
* 1.9.5 Windows EXE의 정적 자산이 현재 소스와 일치한다. 별도 LAN 가짜 서버를 통한 번역 전용 복구, 실제 SRT 저장, 현재 작업 중 수동 대기 추가·자동 항목 승격·이동·제거·현재 묶음 보호, ETA 전달·최종 상태 제거를 확인했다. 실제 음성 인식이나 외부 번역 요청은 호출하지 않았다.
* 실제 복사한 1.9.4 EXE에서 PowerShell 업데이트 도우미를 거쳐 1.9.5로 교체했다. 별도 실패 시나리오에서는 1.9.4로 복귀했다. 양쪽 모두 분석 결과·SRT·대기·클라이언트/호스트 연결 설정·진단 자료 등 8개 파일의 바이트가 동일했고, 직접 생성한 프로세스만 종료했다.
* 합성 브라우저 화면에서 실행 중 추가·정렬·제거·중지·재개와 오류 표시를 확인했다. 375px에서 문서 가로 넘침이 없었고 768px·900px·1280px의 배치를 점검했다. 브라우저 콘솔 오류·경고는 없었다.
* 최종 EXE **99,415,349바이트**, SHA256 **`00ef7d663722eec559922f5fe02aca37af094fa20a0f9fef1ee2be3b9a77b069`**. 업데이트 매니페스트의 버전·크기·해시가 실제 파일과 일치한다.

## 실행 버전과 오류의 구분

작업 착수 시 읽기 전용으로 확인한 이 PC 실행 버전은 1.9.3이었다. 저장소의 최신 실행 파일을 만드는 것만으로 운영 서버가 바뀌지는 않는다. Node/BAT 서버에는 EXE 자동 교체가 없으며 사용자가 최신 코드로 다시 실행해야 한다. 기존 데이터 폴더를 사용하면 주소·연결 코드·결과는 유지한다.

최근 기술 진단에는 1,819구간 중 240구간을 저장한 뒤 번역 검수 요청이 `SUBTITLE_PROVIDER_REFUSAL`로 종료된 기록이 있었다. 구간 수만으로 해당 파일명을 추정하지 않는다. 이는 단순한 처리 지연과 구별해야 하며, 이 업데이트는 요청 거절을 우회하거나 미번역 구간을 완료로 표시하지 않는다.
